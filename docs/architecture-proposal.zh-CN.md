# MotionBase 架构拆分（历史提案）

> **状态：已被单仓 `main` 方案替代。** 本文保留初始双仓设想与当时的验证记录。当前将引擎、`assets/packs/`、作品和 Skills 按目录组织在同一仓库；实际目录、命令与维护方式以[实现架构](architecture.zh-CN.md)为准。

**当时的设计结论：维护两个共享仓库，每部片子拥有自己的作品工作区。** `motionbase` 维护执行引擎、镜头契约和配套 AI Skills。`motionbase-assets` 维护能被多部作品引用的角色、背景、动作、材质以及制作这些资产的源文件。分镜意图、具体镜头、修改历史和交付成片属于作品。独立制作时作品可以是普通目录，团队协作时再为作品建立仓库。

## 1. 谁维护什么

| 位置 | 拥有的数据和代码 | 何时变更 |
| --- | --- | --- |
| `motionbase` | Python CLI、镜头和画风的数据契约、Blender 资产装配、Action 绑定、材质应用、拖尾烘焙、编码、通用校验、项目级 Skills | 改变执行能力、格式或对话工作流时 |
| `motionbase-assets` | 角色模型、骨架、服装、道具、连接位置、背景、舞台锚点、Action、材质库、风格预设、音效，以及生成它们的美术脚本 | 可跨作品复用的美术内容更新时 |
| `productions/<作品>/` | 已接受的创作意图、分镜、镜头时序、画风选择、资产版本、镜头专用覆盖、预览和评审记录 | 用户说“这条片子改一下”时 |
| OwnTake 等宿主 | 创作对话、资产选择、任务状态、预览与版本切换 | 产品交互发生变化时。宿主调用 CLI 或薄适配器，由 MotionBase 执行 Blender 任务 |

两个共享仓库各有独立变化的理由。引擎要保持旧镜头可执行，资产库则可能频繁更新角色和背景。首版把 Skills 跟引擎放在一起，触发语义可以单独调整，调用命令和镜头格式可以随同一版本验证。等有第二个执行引擎也要消费相同的导演流程，再考虑独立发布 Skills。

### 建议目录

| 代码或内容 | 目标路径 |
| --- | --- |
| CLI、格式校验、Blender 调用 | `motionbase/motionbase/` |
| 镜头契约与示例、通用回归 | `motionbase/contracts/`、`motionbase/tests/` |
| 创作与评审两项 Skill | `motionbase/skills/motionbase-direct/`、`motionbase/skills/motionbase-review/` |
| 资产包清单和分类目录 | `motionbase-assets/packs/fox-cliff/pack.json`，同级设 `characters/`、`stages/`、`actions/`、`props/`、`looks/`、`audio/` 和 `source/` |
| 单部作品 | `productions/fox-study/brief.md`、`shots/010.json`、`project.lock.json`、`reviews/`、`build/` |

`pack.json` 和 `project.lock.json` 是建议新增的接口。当前引擎已经支持从镜头相对路径加载 .blend，以及从显式路径加载风格 JSON。第一步可以只调整文件布局。

## 2. 从创作对话抽取两项 Skills

| Skill | 用户怎么说 | Skill 的职责 | 产物 |
| --- | --- | --- | --- |
| `motionbase-direct` | “做一个 5 秒远景，角色跃起，最后收住，背景有纵深。” | 结合已有角色、动作和机位，提出镜头节奏；记录时长、可替换项和用户明确要保留的内容；区分现有资产与待制作资产。只有影响镜头方案的信息缺失时才追问。 | 作品 brief、镜头计划、可执行的 v1 镜头 JSON 与画风选择；确实缺少的资产列入制作清单 |
| `motionbase-review` | “换成木刻，其余都保留。”“落地那一下看起来飘。” | 读取上一版镜头和预览，把反馈定位到镜头、帧区间和责任层；实施最小改动，调用检查和渲染，用旧版对照；保留未能自动判定的审美问题供用户看样。 | 新版预览、改动字段、受影响的资产、检查结果 |

两个 Skill 都通过引擎契约和 CLI 工作。骨长、骨名、着色节点搭建、路径拼接以及数值阈值由代码或资产提供。创作判断随对话调整；同一个输入能确定的检查只实现一次。

**一次修改的具体例子。** 用户说“只换成朱砂木刻”。创作版本记录 `woodblock` 的风格选择，沿用原来的 `shots/010.json` 与资产版本，然后运行 `build` 或 `render`。验收时比较角色骨骼、相机和镜头时长。若用户说“起跳提前四帧，但落地点和时间保持”，现有示例把整段腾跃烘焙在一个 Action 内。应调整动作源的起跳段，生成作品专属 Action 变体，保留落地段，再重新采样拖尾。只平移整条 NLA 片段会连着移动落地时刻。

**多轮沟通的落点。** 新要求依附于明确的作品版本和镜头号。例：`010 / v3` 保留机位、动作和五秒时长，只替换画风。单片调整先保存在作品工作区；等创作者决定将其复用，再提升为共享资产的新版本。这样另一部片子引用的动作不会随本次修改一起变化。

## 3. 建模、背景、动作与约束的边界

| 对象 | 资产库负责 | 作品与引擎分别负责 |
| --- | --- | --- |
| 模型与绑定 | 网格、骨架、静止姿势、骨长、权重、骨骼约束、道具连接点和局部坐标 | 作品指定角色、位置和动作。引擎检查骨架对象、动作数据路径和拖尾绑定骨是否存在 |
| 背景与机位 | 布景、灯光、地面、推荐视角、可见范围。侧视剪纸角色标注适用视角 | 作品拥有最终构图与运镜。当前 `stage.py` 把示例的相机运动写进 `cliff.blend`，将来支持复用同一背景拍两种运镜时，增加镜头级相机轨道覆盖；旧镜头继续使用舞台相机 |
| 动作 | 单对象槽位的 Blender Action、源骨架及兼容信息。示例动作生成器直接读取狐面角色的四肢尺寸，因此两者先在同一资产包内发布 | 作品安排起止帧与段落。引擎绑定与缩放 Action。不同静止姿势或比例的角色，先生成重定向后的兼容动作 |
| 风格与特效 | 色板、纸纹、艺术家制作的材质节点、角色材质用途、道具连接点 | 作品选择风格和特效时段。引擎解释材质用途、读取骨骼变换并烘焙拖尾 |
| 创作与质量约束 | 角色声明“适合侧拍”，动作可声明“第几帧到第几帧是支撑期” | 作品选择“固定机位、接地无滑动”等要求。程序检查声明过的规则，AI 解释失败发生在哪一帧，以及应改哪个资产 |

例如“落地不能滑”涉及三份信息：**舞台资产**提供地面参考，**动作资产**提供支撑脚及接触区间，**检查器**在该区间测量脚相对地面的位移。镜头允许的误差放在作品规则中。把一句“注意不要滑步”写进 Skill 无法替代这项检查。

## 4. 现有工程怎样迁移

| 当前文件或目录 | 建议归属 | 迁移要点 |
| --- | --- | --- |
| `motionbase/__main__.py`、`config.py`、`worker.py`、`look.py`、`trails.py` | 引擎仓 | 保留 `check/build/render` 的 v1 入口。引擎的可分发最小测试素材随引擎保存，以便独立跑 CI |
| `examples/source/character.py`、`choreography.py`、`stage.py`、`art.py`、`sound.py`、`make_assets.py` | 资产仓对应包的 `source/` | 生成器和生成的文件一同维护。资产制作脚本可以使用 Blender，日常渲染只消费发布的资产 |
| `examples/assets/*.blend`、`*.wav`、`presets/*.json` | 资产仓 | 首轮以显式路径引用外部画风。旧版 `styles` 目前只枚举内置目录，迁移期间保留原有按名称查找能力，增加目录发现后再收敛 |
| `examples/leap.json`、`examples/compiled/`、`examples/renders/` | 作品工作区 | 镜头输入纳入版本管理。生成物放 `build/`，只保留值得回看的评审样片与基准 |
| `tests/compare_motion.py`、`tests/asset_contract.py` | 通用比较逻辑归引擎，指定狐面角色的验收数据归资产包 | 现有矩阵比较覆盖相机世界变换和骨骼世界变换。“保持构图”还应比较焦距或正交缩放、画幅与裁切范围 |

### 接口与迁移顺序

1. **保留可执行边界。** 作品交给渲染器的是 `shot.json + style`。当前镜头已声明 `stage`、`actors[].clips`、`trails`、`audio`、帧率与帧数。把美术文件移出引擎后，先用现有接口验证。画风继续通过 `--style` 传入。
2. **加入资产发现和版本固定。** 资产包清单建议记录资产 ID、种类、文件、Blender 集合或 Action 名称，以及骨架兼容标识。作品锁文件记录引擎版本、资产包的精确修订、各镜头选取的风格。编译步骤把选择解析成现有 v1 字段，让 AI 和宿主按 ID 选资产。旧镜头仍可直接渲染。当前的 `motionbase_id` 用于定位对象，骨架兼容性是另一项信息。
3. **交付导演与评审 Skills。** 用“从描述生成五秒镜头”“只换画风”“局部调整起跳时间”三组请求验收。新镜头应能进入 `check`；只换风格应复用原动作；局部动作修改应能指出受影响帧段与保留项。
4. **在实际需要时扩展。** 出现第二种同场景运镜时加相机覆盖。出现第二种骨架时加重定向。多镜头作品由作品层编排顺序与转场，渲染器继续产出单镜头。OwnTake 可以直接接这一边界。

## 5. 本次验证记录

从上一版交付包取出原始文件，在独立临时目录分别放置执行代码、资产包和作品镜头。只重写镜头内的资产路径，并以显式路径加载赛璐璐和木刻预设。用现有 Blender 接口执行了以下比较。

| 检查 | 结果 |
| --- | --- |
| 两种外部风格分别执行 `check` 和 `build` | 两次检查均通过，两份 .blend 均成功生成 |
| 拆分后的赛璐璐与原赛璐璐工程比较 | 150 帧，相机与全部骨骼世界变换的最大矩阵元素差为 0 |
| 拆分后的木刻与原木刻工程比较 | 150 帧，最大矩阵元素差为 0 |
| 拆分后的两种画风互相比较 | 150 帧，最大矩阵元素差为 0 |

本次验证范围是磁盘目录边界、外部画风载入、工程构建和运动一致性。资产清单、版本锁、镜头相机覆盖及两项 Skills 属于后续实现范围。
